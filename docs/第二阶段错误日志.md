## 条目 3：交互环境粘贴多行代码报错（2026-09-13 16:42）

**操作**：在 Python 交互环境里粘贴多行 for 循环做质量检查。

**报错**（3 个，全部是语法/缩进类）：
```
SyntaxError: invalid syntax            ← 粘贴进了未结束的 ... 续行块
IndentationError: unexpected indent    ← 带缩进的行单独粘贴
IndentationError: unexpected indent
IndentationError: unexpected indent
```

**原因**：
1. 第一次粘贴时上一条 for 语句还在等待缩进块（提示符是 `...` 而不是 `>>>`），新代码粘进去把块结构弄乱 → SyntaxError
2. 之后带前导空格的行（如 `    print(...)`）被逐行单独执行，交互模式不允许"裸"缩进 → IndentationError

**教训（交互模式粘贴铁律）**：
- 看提示符：`>>>` 才是干净状态，`...` 说明上一条还没结束（先按回车/退格清掉）
- 多行带缩进的块在交互模式极易粘贴出错 → 要么写成单行（`for t in x[:5]: print(t)`），要么存成 `.py` 文件跑
- 数据分析这类多行代码建议直接写脚本文件，别在交互环境拼

**解决**：改用无缩进的单行写法重跑质量检查（见条目 4）。

## 条目 16：任务 C · STEP 8 错题切分实验——7/10 题（2026-09-15 18:10~18:26）

**操作**：新建 `src\backend\ocr_split.py`，用两条正则对 `all_text.txt`（116 行）切题：
- 章节：`^([一二三四五六七八九十]+)、(.+)$`
- 题号：`^(\d+)\s*[.．、](.+)$`（兼容 `1.`、`4.设`、`3、` 三种写法）

**结果**：
```
共切出 7 道题（选择题 1 / 填空题 2 / 计算题 4）
第1题 选项数 7 个，其余 0 个（符合预期：只有选择题有选项）
```

**分析（本次核心发现：OCR 的题号识别不可靠）**：

| 应切 | 实切 | 丢失原因 |
|---|---|---|
| 选择题 3 题 | 1 题 | 第 1 题题号被 OCR 认成 `Ox100001`（"1." 识别失败）；第 3 题题号行整行丢失，仅残留孤立选项组 |
| 填空题 2 题 | 2 题 | ✅ 完整 |
| 计算题 5 题 | 4 题 | 第 2 题题号行丢失，内容混在手写笔记区（行 68~84） |

**召回率 7/10 = 70%**。结论：**纯正则只能做粗切**，题号丢失是 OCR 的固有缺陷，不是代码 bug。

**下一步补救方案（按成本递增）**：
1. 人工标注 `golden_splits.json` 作为切分验收基准（没有标准答案的优化都是盲调）

## 条目 19：OCR 质量门禁上线——用代码保证下限（2026-09-15 19:20~19:30）

**背景**：条目 18 证明 Prompt 约束救不回最残缺的题，结论是"不能靠模型自觉"。
本条实现条目 18 提出的对策：**入库前打分，低分题不送 AI**。

**实现**：新建 `src\backend\ocr_quality.py`，5 条可解释的评分规则（满分 100，逐条扣分）：

| 规则 | 扣分 | 依据 |
|---|---|---|
| 可疑字符（日文假名/韩文/带重音拉丁）占比 >5% / >2% | -30 / -15 | OCR 认错字最常吐这些 |
| 中文占比 < 10% | -20 | 题干通常有中文说明，纯符号说明切到的是公式碎片 |
| 行首无题号 | -15 | 题号被丢失或误识别（实测 "3." 被认成 "2."） |
| 疑似乱码串（字母数字混杂 ≥5 位）每个 | -10，上限 -30 | 如 `Ox100001`、`xbsy6` |
| 文本 < 30 字符 | -20 | 多半是被切碎的残片 |

设计原则：**每条规则都能说出为什么扣分**，调阈值时有据可依，也方便向老师解释系统为什么拒答。

**集成方式**：
1. `error_items` 增加 `ocr_quality` 字段（老库用 `ALTER TABLE` 自动迁移，已写进 schema.sql）
2. `ocr_to_db.py` 入库时即计算分数
3. `ocr_ai_batch.py` 送 AI 前先过门禁，低分题写入
   `[需人工确认] OCR 可信分 X 低于阈值`，`ai_model` 记为 `quality_gate`

**实测结果（阈值 70，9 道题）**：

| id | 质量分 | 结果 | 主要扣分 |
|---|---|---|---|
| 12（选择题1，题干 `Ox100001`） | **45** | 🚫 拦下 | 可疑字符 + 中文 0% + 2 个乱码串 |
| 13 | 100 | ✅ 送 AI | — |
| 14（选择题4，只剩选项块） | 65 | 🚫 拦下 | 中文 0% + 题号缺失 |
| 15 | 80 | ✅ 送 AI | 中文占比 4% |
| 16（填空2，公式残缺） | 65 | 🚫 拦下 | 可疑字符 + 中文 2.4% |
| 17 | 90 | ✅ 送 AI | 1 个疑似乱码串 |
| 18 / 19 / 20 | 100 | ✅ 送 AI | — |

**最终：送 AI 6 道，拦下 3 道。** 最关键的是 **id=12 被拦下**——
它正是条目 17/18 里 AI 编造得最起劲的那道题，现在根本拿不到。

**已知偏差（待优化）**：
"中文占比 < 10% 扣 20" 这条对**数学题天然不利**（数学题干中文本来就少）。
目前统一阈值，可能误拦部分完整数学题。后续可按学科设不同阈值，
或把"中文占比"换成更通用的"语义完整度"指标。

**意外收获**：本次重跑有 1 次调用超时，被容错逻辑捕获并记入 `ai_logs`（`ok=0`），
补跑成功 —— 说明"失败也要留证据"的设计是对的，失败样本同样是调优材料。

**方法论沉淀（可直接用于结题报告）**：
> 提高 AI 系统可靠性有两条路 —— ①让模型变得更聪明（换 7b、改 Prompt）
> ②让垃圾输入进不了模型（质量门禁）。
> 本项目实测：路线①在 9 题里只多救回 1 题；路线②直接把最坏样本挡在门外。
> **结论：先用工程手段守住下限，再谈模型能力。**

## 条目 20：质量门禁规则迭代——修掉对数学题的误判（2026-09-15 19:25~19:35）

**问题**：条目 19 留了个已知偏差——"中文占比 < 10% 扣 20 分"对数学题不公平

**修法**：把"看中文多不多"换成"**看有没有题干关键词**"

判据更本质：数学题中文再少，"设""求"这类词一定有；纯公式碎片则一个都没有。
**好处是不分学科通用**，不用为数学/英语分别设阈值。

**迭代前后对比**：

| id | 旧分（中文占比） | 新分（题干关键词） | 变化 |
|---|---|---|---|
| 12 | 45 🚫 | 45 🚫 | 一致（真残缺，两版都拦） |
| 14 | 65 🚫 | 65 🚫 | 一致（只剩选项块，无题干） |

| 15 | 80 ✅ | 100 ✅ | 更准确 |
| 其他 | 不变 | 不变 | — |

**方法论沉淀**：

## 条目 27：错题自动分类上线——并识别出"模型背模板"陷阱（2026-09-16 18:00~18:15）

**背景**：统筹文档里"错题数据分类逻辑开发"是 2 号第二阶段任务，一直没做
（字段 `error_type` 在 schema 里预留了但全为 NULL）。3 号前端的错题分布饼图也在等这个字段。

**实现** `src\backend\error_classify.py`：从 AI 解析文本里规则抽取四类
（concept 概念不清 / calculation 计算失误 / misread 审题偏差 / method 方法缺失）。

**关键设计 —— 识别"模板列举"陷阱**：

扫描 7 道已解析错题时发现，0.5b 经常这样输出：
```
2. 错误原因归类：概念不清，计算失误，审题偏差，方法缺失。
```
**这不是分类，是把四类当模板背了一遍。** 如果按关键词计数，这道题会同时命中四类，
分类统计直接失真。所以加了规则：
```python
if 同一段里出现 ≥3 个精确类别词: 判定为 template，分类置 NULL
```

**置信度机制**（新增 `error_type_conf` 字段）：
| 值 | 含义 |
|---|---|
| `high` | 只命中一个类别，可信 |
| `low` | 命中多个取最多的，或靠宽松词频推断 |
| `template` | 模型在背模板，未真分类 |
| `none` | 完全没有可用信息 |

**实测结果（7 道有 AI 解析的题）**：

| 分类 | 置信度 | 题数 |
|---|---|---|
| 未分类 | template | **5** |
| 计算失误 | high | 1 |
| 计算失误 | low | 1 |

**结论**：
1. 分类链路通了，脚本幂等，**等 7b 到位后重跑一条命令即可**（`python error_classify.py --apply`）
2. 但当前 0.5b 下 **71% 的题分不出来**——不是规则不好，是模型输出本身没有分类信息。
   **再次印证：不要给低质量输出做花哨的下游处理，先解决源头**
3. 分类不出来的题保持 NULL，**绝不瞎填**（与质量门禁同一条原则）

- `study_stats.collect_stats` 增加 `by_error_type` 分布，直接供 3 号画饼图

## 39. judge_fragment 7B 重测：4/5 可复现，但兜底不能撤（2026-10-11）

### 39.1 为什么要重测

0.5b 时代实测该场景完全随机（3 题 × 3 次无一一致），判错会 INSERT 假题，
所以加了"多轮不一致强制判 C"的兜底——等于这个功能一直没真正启用。
7b 装好后必须用同一批题、同一脚本重测，才知道兜底能不能撤。

脚本：`tools/retest_judge_7b.py`（只读正式库，不写数据）。
样本：库里按 `ocr_quality` 升序取的连续三行，中间行当待判断片段。

### 39.2 结果：新旧对照

| 模型 | 三次判定完全一致 | 多数派分布 |
|---|---|---|
| `qwen2.5:0.5b` | **0 / 5** | A×1、B×4（每次都在变） |
| `qwen2.5:7b-instruct-q4_K_M` | **4 / 5** | B×4、A×1 |

0.5b 的理由肉眼可见是胡话，比如"z = x 在 (0,0) 处的偏导数存在，
因此该题的答案是 B"——把选项字母当成了答案；
"在判别题中，判断题应该选择 A"。7b 给的理由是像样的
（"符合题干和选项的形式，可能是选择题题干的开头"）。

### 39.3 结论：改善明显，但**兜底保留**

7b 从 0/5 到 4/5 是质的变化，但仍有 1 例摇摆（id=15 三次跑出 A/B/A）。
这个场景判错会往库里补一道不存在的题，**漏一道题比补一道假题划算**，
所以只要不是 100% 可复现，兜底就不能撤。

### 39.4 顺带加了一条硬约束

原校验只管 `choice` 是不是 A/B/C。但三个选项里**只有 B 会写库**
（判 B = "这是一道被漏掉的独立题" → ocr_recover 会 INSERT 新题），
风险最大，却没有任何字段要求。

实测 7b 判 B 时确实会填 `stem`（"设 z = arctan((x-y)^2+(x+y)^2)/(x-y)"），
但**那是模型表现，不是契约保证**。已加成硬约束：

```python
if ch == "B" and not str(data.get("stem", "")).strip():
    return False, "choice=B 必须同时给出 stem（题干），否则无法安全补题"
```

测试已锁（v2-6：无 stem 被拒 / 有 stem 放行 / 判 C 不需要 stem）。

### 39.5 样本本身的局限（如实记）

样本是**人工构造的相邻关系**——库里按 `ocr_quality` 排序后取连续三行，
它们在原始试卷里未必真的相邻。所以"多数派判 B"不能直接当准确率读：
这些片段本身就是完整题目，判 B 恰好是对的。

**能下的结论只有"可复现性"，下不了"准确率"结论。**
要测准确率得有标注过的真实切分样本，目前没有。

### 45.3 占位符加载：队长的意见成立，我上份报告描述不准

实测（篡改 `_PLACEHOLDERS` 缓存后第二次调用直接返回篡改值 → 证明不重读文件）：

```
>>> set(gateway_placeholders())        # {'请填写分析结果'}
>>> ai._PLACEHOLDERS = {'探针_缓存生效'}
>>> set(gateway_placeholders())        # {'探针_缓存生效'}  ← 没去重读
```

更狠的实验：**同一进程内先建立缓存、再替换磁盘上的包** → 仍读不到新值。
所以"每次重新 exec"是错的，且**换包后必须重启后端**（已写进 docstring）。
另：加载时确实临时 insert/remove 了 sys.path，我写的"不污染 sys.path"也不准。

实验收尾务必核对 SHA256 与官方 SHA256SUMS 一致（本次一致，包没被弄脏）。
