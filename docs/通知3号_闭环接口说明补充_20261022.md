## 二 你问的两个问题

### 2.1 `GET /errors` 里有没有 `wrong_answer_text` / `answer_text`

**有，返回了。** 这两个字段在列表接口里就带着，不需要再单独查详情。

```
GET /errors → {"count": N, "items": [ {...,"wrong_answer_text": "...",
                                       "answer_text": "...", ...} ]}
```

你没看到同样是版本旧导致的。

### 2.2 新录入的题 `review_flag` 是 null，是默认 `pending_review` 吗

**不是。默认就是 NULL，请不要把 null 当成「待复核」来渲染。**

这是有意的区分：

| 值 | 含义 | 会不会计入统计 |
|---|---|---|
| `NULL` | 还没走过任何流程，既没分析也没确认 | 不计入 |
| `pending_review` | 已经被退回/推翻过，等着人再看一眼 | 不计入 |
| `confirmed` | 已人工确认且有合法分类 | **计入** |
| `rejected` | 人工判定 AI 归因不成立 | 不计入 |

（正式库实测：11 条错题里 4 条 NULL、7 条 `pending_review`。）

前端建议：**null 显示为「未处理」，pending_review 显示为「待复核」**，
两个是不同的视觉状态，别合并。

## 三 补齐的字段说明（你要的那几项）

### 3.1 `PATCH /errors/{id}/answer` —— 修改作答

请求体：

```json
{ "answer": "学生的原始作答", "reference_answer": "参考答案" }
```

⚠️ **字段名对照（上次没写清楚，这里定死）**：

| 前端传的字段 | 数据库里的列 | 含义 |
|---|---|---|
| `answer` | `wrong_answer_text` | **学生自己的作答** |
| `reference_answer` | `answer_text` | **参考答案**（标准答案） |

两个字段**传 null 表示不修改**（保留原值），传空串表示清空。

返回体新增了三个字段，前端可以直接用来决定要不要刷新确认态：

```json
{
  "id": 12,
  "changed": true,
  "review_flag": "pending_review",
  "previous_conclusion_invalidated": true,
  "answer_recorded": true,
  "reference_answer_recorded": true,
  "note": "作答已变更：已确认分类退回待复核，旧结论已归档"
}
```

| 字段 | 含义 |
|---|---|
| `changed` | 内容是不是真的变了（去掉首尾空白后比较）。**重复提交相同内容时为 false，且不会动状态** |
| `review_flag` | 改动后的状态 |
| `previous_conclusion_invalidated` | 旧结论是否被推翻并归档了 |
| `note` | 给人看的中文说明，可以直接弹提示 |

### 3.2 四种情况的实际行为（实测过，照这个对）

| 情况 | changed | 归档 | review_flag 变化 |
|---|---|---|---|
| 原本 **confirmed**，作答改了 | true | 有 | confirmed → **pending_review** |
| 有分类但**没有确认**（review_flag 是 NULL），作答改了 | true | 有 | **保持 NULL 不变** |
| 原本**没有任何结论**，作答改了 | true | 无 | 保持 NULL 不变 |
| 提交的内容跟原来**一模一样** | **false** | 无 | 完全不动（手抖点两次不会刷掉确认） |

⚠️ **注意第二行**：只有 `confirmed` 才会退回待复核，其他状态保持原值。
这是当前实现，**别在前端写成「改了作答一律变待复核」**。

### 3.3 `POST /errors/{id}/analyze` —— 再次分析

```bash
POST /errors/{id}/analyze            # 普通分析
POST /errors/{id}/analyze?force=true # 强制重跑（会推翻旧的已确认分类）
```

已确认的题不加 force → **返回 409**，消息是「该条已人工确认分类；要重跑请加 ?force=true」。

成功返回（关键字段）：

```json
{
  "id": 12, "code": 0, "ok": true,
  "suggested_error_type": "calculation_error",
  "suggested_error_type_label": "计算失误",
  "error_confidence": 0.8,
  "review_flag": "pending_review",
  "previous_review_flag": "confirmed",
  "answer_recorded": true,
  "note": "AI 候选错因，未经人工确认不计入统计"
}
```

| 字段 | 含义 |
|---|---|
| `suggested_error_type` | AI 给的**候选**分类，四个取值之一 |
| `suggested_error_type_label` | 中文标签（概念不清 / 计算失误 / 审题偏差 / 方法缺失） |
| `previous_review_flag` | force 之前是什么状态，让你知道推翻了什么 |
| `review_flag` | 现在是 pending_review |
| `note` | 明确告诉你：**未经人工确认不计入统计** |

**分析失败时不改状态**：

```json
{"id": 12, "code": 1, "ok": false, "error": "...", "raw_reason": "..."}
```

失败前后 other 字段一个都不动—— `analysis`、`error_confidence`、`review_flag` 都不会被清空。
前端拿到 `ok=false` 时**不用刷新状态卡片**，原样保留即可。

### 3.4 `PATCH /errors/{id}/review` —— 人工确认

```json
{ "decision": "confirmed", "error_type": "calculation_error", "note": "人工备注" }
```

- `decision` 只有 `confirmed` 和 `rejected` 两种
- `error_type` 四个取值：`concept_misunderstanding` / `calculation_error` / `misread_question` / `method_gap`
- `decision=rejected` 时不需要给 `error_type`

**可能发生的两个错误**：

| HTTP | 什么时候 | 返回 |
|---|---|---|
| 400 | `confirmed` 但既没传合法 `error_type`、库里也没有可沿用的分类 | 中文说明，且**状态一点没改** |
| 400 | 传了不在四个取值内的 `error_type` | 同上 |

这条 400 很容易在页面上误触发：**用户点「确认」但没选错因类型**。
建议前端把「确认」按钮在没选类型时禁用掉。

### 3.5 `GET /errors/{id}/history` —— 查历史归档

⚠️ **返回体里的字段名是 `history`，不是 `items`**（跟列表接口不一样，别套错）：

```json
{
  "id": 12,
  "count": 1,
  "history": [
    { "id": 1, "event": "answer_changed", "review_flag": "confirmed",
      "error_type": "calculation_error", "wrong_answer_text": "旧作答",
      "reason": "学生/参考答案被修改，原已确认分类退回待复核",
      "created_at": "2026-10-22 20:05:31" }
  ]
}
```

`event` 三种取值：`answer_changed`（改了作答）/ `reanalyzed`（force 重跑）/ `review_changed`（人工覆盖）。

### 3.6 计划参数拒绝规则（学习计划场景要注意）

生成学习计划时的两个参数 `plan_days`、`available_minutes_per_day`：

| 传的值 | 后端行为 |
|---|---|
| 不传 / null | 用默认值 3 天、60 分钟 |
| 正常整数 `"3"` / `3` | 正常 |
| 超范围（比如 99 天） | **夹取到范围内**（1-7 天、1-480 分钟），不报错 |
| `"3天"` 这类带单位的字符串 | **直接报错**，返回 code=2，**不调模型** |
| 布尔、小数、数组、对象、空串 | 同上，**报错** |

改以前是静默降级（"3天" 会变成 3 天），**现在会直接失败**。
前端要做类型和范围校验，别让用户把带单位的字符串传上来。
