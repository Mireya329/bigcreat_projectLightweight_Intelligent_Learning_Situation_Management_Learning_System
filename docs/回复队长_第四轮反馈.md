## 三 新发现（一）：网关示例占位符能混进正式答案

### 现象

在测试库副本上复测 id15，7B 三次返回的都是：

```json
{"answer": "请填写分析结果", "solution": ["计算f(x,y)关于x的一阶偏导数fx(x,y)。", "..."],
 "error_type": "concept_misunderstanding", "error_confidence": 0.8, ...}
```

`请填写分析结果` 是网关 `output_shape()` 给字符串字段的**示例占位文本**，
模型照抄了它。问题在于：

- 它不是空字符串，所以 v2.1 的空答案兜底**不会触发**；
- schema 只查 `minLength=1`，占位符**照样通过校验**；
- 于是这个假答案会一路走到渲染和入库。

原始响应已保存在 `docs/logs/id15_v21_raw_20261017_200814.json`，可供排查。

### 我侧的处置

没有改队长包。在 `ai_interface` 加了 `strip_placeholders()`：
在 normalize 阶段把等于占位符的值剔除，置空并打 `answer_placeholder=True`
标记，渲染时写明"（模型给出的是示例占位文本，已剔除，非真实答案）"。

占位符的值**从包里现读**（调用 `captain_ai.output_shape`），不硬编码，
您后续改了示例文案我侧会跟着变。已加 8 项断言锁死该行为，包括"真实答案不得被误伤"。

### 建议（请您判断）

是否需要在网关侧也堵一下？例如校验时拒绝等于 `output_shape` 示例值的字符串，
或者把示例文案改成一个不可能被当成答案的形式。这属于您维护的网关规则，我不擅自改。

## 四 新发现（二）：我方 bug，已修

### 现象

同一条 id15、同一个模型：

- 直连网关复测 → **3/3 成功**
- 走后端 `analyze_error` → **4/4 失败**，`data.answer: empty text`

结果完全相反，说明差异不在您那边。

### 排查与定位

把后端实际发出的请求体抓出来对比：

```
后端发的：user_context = {"plan_days": 3, "available_minutes_per_day": 60}
直连脚本：user_context = {}
```

我方 `normalize_user_context()` **不分场景**地注入排计划用的两个参数。
它们对 `error_analysis` 毫无用处，却会进网关 prompt，实测让 7B 在这道题上
稳定输出空答案，进而触发您说的"无明确结论标记 → 重试或失败"路径。

### 修复

改为只在 `study_plan` 场景、或调用方显式传了时才注入。改完 `user_context={}`，
后端路径 3/3 成功。协议测试的断言也同步更新了语义。

这条的经验是：**"直连能过"不等于"端到端能过"**，中间层的参数注入会改变模型行为。
