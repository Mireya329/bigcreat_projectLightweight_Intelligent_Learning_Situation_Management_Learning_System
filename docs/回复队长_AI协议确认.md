## 3. 需要你定：`error_confidence < 0.5` 这个闸门拦不住

协议里定的"置信度 <0.5 打待人工复核、不入库"，前提是置信度能反映模型的真实把握度。

实测：**能反映一部分，但不够用。**

好的一面——模型确实分得清看得懂看不懂：干净题给 1，OCR 残题给 0。

坏的一面——置信度本身也是飘的。同一道题跑三次，置信度在 0.0 和 1.0 之间跳，
而且它会在**随机分类上给满把握**（id=16 第二次跑 `method_gap` conf=1.0，
第一次是 `calculation_error` conf=0）。

也就是说，模型会自信地给出一个错的分类。这道闸门拦得住"模型自认没把握"的，
拦不住"模型抽错了但很自信"的。

**我侧先做了一版补救给你参考**（`call_ai_stable()`）：同一题跑 2 轮，

- 分类一致 → 照常入库，置信度取两轮最小值（保守）
- 不一致 → 解析保留，但置信度置 0，自动转人工复核

刻意复用了你定的 `<0.5 不入库` 规则，没新造机制。
实测 7 道错题：**1 道一致，6 道被拦下**。代价是推理次数翻倍（单题 10~17 秒）。

开关 `STABILITY_CHECK`，现在默认关，等你定口径。
如果你的协议要收这条，建议措辞：**"同一题两次调用 error_type 不一致时，
保留解析、error_type 置空并转人工复核"**——比单纯加阈值靠谱，因为它不依赖模型自评。

## 4. 协议里有个小漏洞：label 会和 code 错配

协议给了 `error_type` 和 `error_type_label` 两个字段，但没约束它们必须一致。
实测模型会填错：

| error_type | 模型给的 label | 应该是 |
|---|---|---|
| misread_question | 函数定义错误 | 审题偏差 |
| method_gap | 计算失误 | 方法缺失 |
| method_gap | 区间外函数与区间内函数的函数关系 | 方法缺失 |

**我侧的处理**：不信模型的 label，以 `error_type` 为准按映射表自己生成。
你那边如果也直接用模型的 label，建议同样处理一下。
