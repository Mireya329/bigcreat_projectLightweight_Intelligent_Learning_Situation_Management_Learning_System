# 数据库安装与升级说明

**适用范围**：后端 `src/backend`、`src/backend/db` 下的全部脚本。
**面向**：所有要在自己电脑上跑这套后端的成员（含队长、一号、三号、四号）。
**日期**：2026-10-22，针对队长《对二号第五轮反馈的组长回复》第二节第 4 条：
"归档表是部署依赖，不能只在自己的测试库建好表，而遗漏其他成员电脑的部署步骤。"

---

## 零 先记住这三句话

1. **路径一律写绝对路径**。相对路径会按你当前所在目录解析，实测把 `../data/x.db` 跑成了 `src/data/x.db`。
2. **跑之前看一眼脚本打印的第一行**。所有脚本都会打印 `[xxx] 实际绝对路径：...`，确认是你要的库再继续。
3. **给已经启动的服务设环境变量没有用**。环境变量只影响**当前进程**，改它不会让正在跑的后端换库。要换库就得重启服务。

## 二 三种路径，别混用

| 场景 | 用哪个脚本 | 会不会动已有数据 |
|---|---|---|
| 全新机器、还没有库 | `init_db.py` | 新建，不影响任何东西 |
| 已经有库、要升级结构 | 对应的 `migrate_*.py` | 只加表/加字段，不动已有行 |
| 不确定要不要升级 | 先跑 `--check` | 完全只读 |

### 2.1 全新安装

```bash
cd D:\bigcreat_project
venv\Scripts\python.exe src\backend\db\init_db.py --db "D:\bigcreat_project\data\learning.db"
```

**实测结果**（2026-10-22）：一次建成 **18 张业务表**，`integrity_check` = `ok`。

```
ai_logs / anki_cards / chapter_records / dicts / error_item_tags / error_items /
error_review_history / knowledge_tags / question_bank / question_bank_conflicts /
quiz_records / review_schedules / schema_migrations / study_sessions / subjects /
users / word_records / words
```

### 2.2 旧库升级（最常见）

按下面顺序跑，**每个都支持 `--check` 先看一眼**：

```bash
venv\Scripts\python.exe src\backend\db\migrate_review_history.py    --db "<库绝对路径>" --check
venv\Scripts\python.exe src\backend\db\migrate_review_history.py    --db "<库绝对路径>"

venv\Scripts\python.exe src\backend\db\migrate_question_bank_v2.py  --db "<库绝对路径>" --check
venv\Scripts\python.exe src\backend\db\migrate_question_bank_v2.py  --db "<库绝对路径>"
```

**实测结果**（2026-10-22，拿迁前的备份当"旧库"跑）：

| 步骤 | 输出 |
|---|---|
| 迁移前 check | `error_review_history 不存在`　退出码 **1** |
| 执行迁移 | `error_review_history 已创建，字段 12 个` |
| 迁移后 check | `error_review_history 已存在`　退出码 **0** |
| error_items 行数 | 迁移前后都是 11，**没有被碰到** |
| integrity_check | ok |

### 2.3 重复执行

连续跑三次同一个迁移脚本：

```
第 1 次：error_review_history 原已存在，字段 12 个
第 2 次：error_review_history 原已存在，字段 12 个
第 3 次：error_review_history 原已存在，字段 12 个
归档表条数 0，error_items 仍 11 行，integrity ok
```

**结论：可以放心重复跑，跑几次都不会多数据、不会报错。**

## 三 备份与回退

### 3.1 备份

```bash
cd D:\bigcreat_project
venv\Scripts\python.exe -c "
import sys; sys.path.insert(0,'src/backend/db')
import db, db_backup
db_backup.backup_database('写清楚为什么备份', db.resolve_db_path())
"
```

备份会做三层校验（`integrity_check` → 关键表 → 必要字段），并且**与源库逐表比对行数**，
输出 `与源库逐表行数比对：一致` 才算成功。文件落在 `data/backups/`，文件名带原因和时间戳。

### 3.2 回退

把备份文件复制回去覆盖即可：

```bash
cp "data/backups/learning_<原因>_<时间戳>.db" data/learning.db
```

> ⚠️ 覆盖前确认当前库里没有备份之后新产生的重要数据。

## 四 数据库选择的优先级（很重要）

只有一个地方决定用哪个库：`src/backend/db/db.py` 的 `resolve_db_path()`。
优先级固定为：

```
命令行 --db  >  环境变量 LEARNING_DB_PATH  >  默认 data/learning.db
```

三种写法等价，推荐第一种（最不容易搞错）：

```bash
# ①推荐：命令行
venv\Scripts\python.exe src\backend\db\migrate_review_history.py --db "D:\xxx\test.db"

# ②环境变量（Windows Git Bash）
LEARNING_DB_PATH="D:\xxx\test.db" venv\Scripts\python.exe src\backend\db\migrate_review_history.py

# ③什么都不给 = 正式库，跑之前一定先看打印
```

### 4.1 这里曾经有一个危险的 bug（已修，写出来引以为戒）

2026-10-22 实测发现：`migrate_review_history.py` 之类的老脚本**根本不认 `--db`**——
`DB_PATH` 是 import 时就固化的默认值。跑
`migrate_review_history.py --db 别的库.db` 时参数被无视，脚本照样写到正式库，**而且一句话都不提示**。

这是最危险的一类 bug：你以为在做 A，实际在做 B。
现在所有 `db/` 下的脚本都在 import 之后调了 `db.apply_cli_db()`，`--db` 统一生效。

**判断方法**：跑脚本时看它打印的 `[xxx] 实际绝对路径` 是不是你要的那个。

## 五 跑完之后怎么验收

### 5.1 静态检查

```bash
venv\Scripts\python.exe -c "
import sqlite3
c=sqlite3.connect(r'D:\bigcreat_project\data\learning.db')
print('表数量:', len(c.execute(\"select name from sqlite_master where type='table' and name not like 'sqlite_%'\").fetchall()))
print('归档表存在:', bool(c.execute(\"select count(*) from sqlite_master where name='error_review_history'\").fetchone()[0]))
print('错题行数:', c.execute('select count(*) from error_items').fetchone()[0])
print('题库行数:', c.execute('select count(*) from question_bank').fetchone()[0])
print('integrity:', c.execute('pragma integrity_check').fetchone()[0])
print('外键:', c.execute('pragma foreign_key_check').fetchall())
"
```

预期：表 18 张、归档表存在、`integrity` = ok、外键检查返回空列表。

## 六 附：归档表到底干什么的

`error_review_history` 只做**追加归档**，不参与任何统计。统计口径仍然只看
`error_items.review_flag`。

会在三种时机产生记录，都是为了"旧结论不能凭空消失"：

| event | 什么时候 |
|---|---|
| `answer_changed` | 学生/参考答案被改，旧的已确认分类退回待复核 |
| `reanalyzed` | force 重跑分析产生了新的候选结论 |
| `review_changed` | 人工复核覆盖了一个已有的已确认结论 |

查某题的归档：`GET /errors/{id}/history`。

> 说明：`api.py` 里留了一份建表兜底（缺表时接口会自己建），
> 实测两份 DDL **字段完全一致**（都是 12 列），所以先跑到谁都不会造成结构分歧。
> 但**不要依赖这个兜底**，正式部署还是按第二节跑迁移。
