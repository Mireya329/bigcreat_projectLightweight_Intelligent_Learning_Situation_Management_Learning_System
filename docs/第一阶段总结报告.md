
- **为什么用官方源不用清华源**：PaddlePaddle 官方源在国内本身很快，且保证版本正确
- **为什么装 CPU 版**：我们是笔记本（RTX 4060 是给 Ollama 用的），PaddlePaddle GPU 版要配 CUDA 工具链，第一阶段先用 CPU 版跑通功能，第二阶段再考虑 GPU 加速

> ⚠️ **可能遇到的报错 1**（Windows 特有）：
> ```

> **解决**：直接**把命令重跑一遍**，一般就过了。如果留下 `~umpy` 这种波浪号开头的残留目录，用 Python 清理：
> ```bash
> venv\Scripts\python.exe -c "import shutil; shutil.rmtree(r'D:\bigcreat_project\venv\Lib\site-packages\~umpy')"

### 1.4 跑第一个识别 Demo（此时必踩一个坑）

先做一张测试图 `data\test_ocr.jpg`（随便用画图写三行中文打印题拍照/截图都行），然后：

```bash
cd D:\bigcreat_project

```

在交互环境里输入：
```python
from paddleocr import PaddleOCR
ocr = PaddleOCR(use_textline_orientation=True, lang="ch")     # ← 这样写会报错！
result = ocr.predict("data/test_ocr.jpg")
```

> ⚠️ **必踩的坑 3**：上面的写法会报：
> ```
> NotImplementedError: ConvertPirAttribute2RuntimeAttribute not support
> [pir::ArrayAttribute<pir::DoubleAttribute>] (onednn_instruction.cc)
> ```
> **原因**：CPU 的 oneDNN 加速路径不支持部分算子属性，这是本机环境的实际 bug，换版本也躲不掉（我试过 3.0.0、3.2.0、paddleocr 3.1.0、2.7.3 共四种组合，全部失败）。

**正确写法（背下来，本项目所有 OCR 代码都要带这个参数）**：
```python
ocr = PaddleOCR(use_textline_orientation=True, lang="ch", enable_mkldnn=False)
```
- `lang="ch"`：中英文混合识别
- `use_textline_orientation=True`：自动判断每行文字方向（试卷斜着拍也能救）
- **`enable_mkldnn=False`：关闭 oneDNN 加速，绕开崩溃 bug，必须加**

**首次运行会发生什么**：自动下载 5 个模型到 `C:\Users\<你的用户名>\.paddlex\official_models\`（约 177MB：文档矫正 UVDoc ×1、方向分类 ×2、PP-OCRv6 检测+识别 ×2）。下载需要几分钟，之后**全程离线可用**——这正是我们项目"本地离线"定位需要的。

**预期输出**（我的测试图识别结果）：
```

.什么是操作系统的死锁？        ← 序号"1"被误识别为"."，已知小瑕疵
2. 简述哈希表的冲突解决方法。
```
三行中文主体全对，Demo 通过 ✅

## 第 4 步：安装 Ollama 便携版（最难下载的一个，全程攻坚）

### 4.1 为什么不用官方安装包

官方下载地址会跳转 GitHub，国内直连 443 被墙。我依次试过：ollama.com 直链 ❌ → 清华镜像（没有这个包）❌ → ghfast.top 代理（超时）❌ → gh-proxy.com 单线程（12KB/s，1.36GB 要下 30 小时）❌。

### 4.2 最终方案：32 线程分段下载（自写脚本）

原理：代理按**每条连接**限速 12KB/s，那就开 32 条连接各下一段（HTTP Range 请求），速度叠加到 **3.7MB/s，40 分钟下完**。脚本在 `D:\bigcreat_project\installers\dl_ollama.py`。

**如果以后要复现**：核心步骤是——
1. 先 `HEAD` 请求拿到文件总大小和"是否支持 Range"（Accept-Ranges: bytes）
2. 把文件按 32MB 一段切给 32 个线程
3. 每线程 `Range: bytes=start-end` 只下自己那段
4. 全部下完按顺序拼起来

### 4.3 下载后必做完整性校验（分段下载容易有坏块）

我的 zip 就有 2 个文件 CRC 校验失败（都是 CUDA 库：cublas64_12.dll、cublasLt64_12.dll）。**不用整个重下**：解析 zip 内部结构拿到损坏文件的字节区间，只重下那几百 MB 覆盖回去（`fix_ollama_zip.py`）。

### 4.4 解压到 D 盘并验证

解压到 `D:\Ollama\`（便携版解压即用，不写注册表，完全放 D 盘），然后建一个 `D:\Ollama\启动Ollama.bat`，内容两行：

```bat
@echo off
D:\Ollama\ollama.exe serve
```

**以后每次用：双击这个 bat，弹出黑窗口就是服务在跑，关窗口就是停服务。**

验证（开着 bat 窗口，另开一个 CMD）：
```bash
D:\Ollama\ollama.exe --version
# 预期：client version is 0.33.2

curl http://127.0.0.1:11434/api/version
# 预期：{"version":"0.33.2"}
```

## 第 5 步：写 AI 接口预留层（`src\backend\ai_interface.py`）

### 5.1 为什么第一步就写接口

因为它是全后端和 AI 之间的**唯一通道**：先冻结函数签名（输入输出结构），前端和 OCR 模块立刻可以对着 mock 数据开发，不用等组长部署完模型。等第二阶段 Ollama + qwen2.5:7b 就绪，**只改一行 `MOCK_MODE = False`，全后端零改动切换真实推理**。

### 5.2 核心设计（文件里都有，这里讲思路）

- 统一入口 `call_ai(AIRequest)`，内部根据 `MOCK_MODE` 决定返回占位数据还是真调 Ollama
- 五个业务函数：`explain_wrong_question`（错题解析）/ `knowledge_qa`（知识问答）/ `diagnose_weakness`（薄弱诊断）/ `school_advice`（择校推荐）/ `polish_essay`（作文批改）
- 衔接函数 `ocr_result_to_question()`：OCR 的多行输出 → 拼成完整题目字符串
- 探活函数 `check_ollama_alive()`：对接组长时先跑这个确认服务在线
- 配置区就三个值：`OLLAMA_BASE_URL = "http://localhost:11434"`、`MODEL_NAME = "qwen2.5:7b"`（组长定了改这里）、`REQUEST_TIMEOUT = 120`

## 第 6 步：真实试卷 OCR 测试（第二难的攻坚）

### 6.1 测试素材

一张数学分析测验长图（1280×3893 像素，含手写批注）。先用一张"智记校园"Logo 图单独测过（置信度 1.000，证明艺术字都识别得很好），再上真实试卷。

> ⚠️ **坑 6：中文路径**。原图在微信文件夹里（路径全中文），OCR 读不到，报"信息: 用提供的模式无法找到文件"。**解决：复制到 `data\test_real_exam.png` 英文路径再处理。**

### 6.2 发现大图静默崩溃 bug（第一阶段最硬的骨头）

直接把整张图喂给 `ocr.predict()`——**不报任何 Python 错误，进程直接退出**。我做了逐级测试锁定规律：

| 图片尺寸 | 结果 |
|---|---|
| 800×300 | ✅ 正常 |
| 1280×480 | ✅ 正常 |
| 1280×950（缩放后） | ✅ 正常 |
| 1280×1200（缩放后） | ❌ 崩溃 |
| 1280×3893（原图） | ❌ 崩溃 |

根因：oneDNN 的算子属性转换 bug（`onednn_instruction.cc:118`），在特定图片尺寸下触发。我试了 7 种方案全失败：`enable_mkldnn=False` ❌、环境变量 `FLAGS_use_mkldnn='0'` ❌、`paddle.set_flags` ❌、降级 3.0.0/3.2.0/paddleocr 3.1.0/2.7.3 ❌❌❌❌。

### 6.3 最终生产方案：切片 + 子进程隔离

**两条铁律（第二阶段写代码必须遵守）**：
1. **图片切片**：高度 ≤300px 一片（宽度 ≤1280），每片单独存 PNG
2. **一片一个子进程**：同一个 Python 进程里第 2 次调 `predict()` 会因 paddle 内部状态污染失败，所以每片用 `subprocess` 起一个全新 Python 进程跑完即退

三个脚本配合（都在 `src\backend\`，可直接复用）：
1. `ocr_run_real_exam3.py`——把长图切成 13 片存到 `data\ocr_real_test\slices\`
2. `ocr_one_slice.py`——worker：接收（图片路径，输出JSON路径）两个参数，跑一片
3. `ocr_summarize.py`——把 13 片的 JSON 汇总成最终结果

### 6.4 测试结果与三个关键发现

| 指标 | 数值 |
|---|---|
| 切片成功 | 11/13（04、06 两片因并发干扰失败，可单独补跑） |
| 识别行数 | 182 行 |
| 平均置信度 | 0.826（>0.9 的占 47.3%） |

三个关键发现（第二阶段的活）：
1. **性能严重不达标**：实测 ~600 秒/片，预期 1–3 秒 → 第二阶段头号任务（模型常驻、`max_side_len` 降到 960、换轻量模型）
2. **手写批注几乎全挂**：红蓝笔字基本识别不出 → 需手写专用模型
3. **数学公式漏检**：只识别出 lim、Δx 这类简单符号，分数根号全漏 → 需公式识别增强
