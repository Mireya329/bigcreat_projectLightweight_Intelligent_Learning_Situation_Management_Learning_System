# AI 协议真机联调报告（2026-09-21）

模型：`qwen2.5:0.5b`（494M，Q4_K_M）　Ollama：`0.33.2`　本机 CPU 推理
脚本：`src/backend/ai_live_test.py`、`src/backend/ai_repeat_test.py`

---

## 一、结论先行

| 问题 | 答案 |
|---|---|
| `format=json` 能不能逼出合法 JSON？ | **能**。7 题里 6 题一次或重试后给出合法 JSON |
| 那协议是不是就解决问题了？ | **没有**。格式通了，语义没通 |
| 分类结果可信吗？ | **不可信**。同一输入跑 3 次，5 题里只有 1 题分类稳定 |
| 置信度能当质量闸门吗？ | **不能**。模型会在随机分类上给 1.0 的高置信度 |

**一句话**：协议把"模型说人话"改造成了"模型说 JSON"，这一步是有效的；
但 0.5b 的分类内容仍然是随机的，`error_confidence < 0.5 不入库`这道闸门拦不住它。

## 二、A 层：裸测 format=json

同一 prompt 分别用 `format=json` 和完全无约束各打一次：

| 用例 | format=json | 无约束 | 备注 |
|---|---|---|---|
| 四选一 | ✅ 7065ms | ✅ 2137ms | 都输出 `{"choice":"A"}` |
| 多字段 | ✅ 2237ms | ✅ 2118ms | 都输出 `{"answer":"北京","confidence":1.0}` |
| 错题分类 | ✅ 2542ms | ❌ 2515ms | 无约束那次输出被截断，解析失败 |

**结论**：`format=json` 确实提高了产出合法 JSON 的稳定性，队长这个约束是有效的。

但要注意第三个用例的内容：

```json
{"solution": "calculation_error", "error_confidence": 1,
 "error_reason": "lim(0→x) sin(0)/x = 0", "method_gap": false}
```

`error_type` 字段**根本没出现**，分类值被塞进了 `solution`，还多出一个 `method_gap: false`。
——JSON 合法，语义全错。这正是后面 B 层要暴露的问题的预兆。

## 三、B 层：走完整流程（7 道真实 OCR 错题）

同一批题**跑了两轮**，这是最能说明问题的一组数据：

| 错题 id | 第一轮 | 第二轮 |
|---|---|---|
| 13 | `method_gap` conf=0 | `method_gap` conf=**0.8** |
| 14 | `misread_question` conf=0 | `calculation_error` conf=**1.0** |
| 15 | `misread_question` conf=0 | `calculation_error` conf=0.0 |
| 16 | `calculation_error` conf=0 | `method_gap` conf=**1.0**（触发重试） |
| 17 | `calculation_error` conf=0 | `calculation_error` conf=0.0 |
| 18 | `calculation_error` conf=0 | `method_gap` conf=0.0 |
| 12 | — | 124 秒超时降级 |

第一轮 7/7 通过、置信度全 0；第二轮 6/7 通过、置信度 `[0.8, 1.0, 0.0, 1.0, 0.0, 0.0]`。
**同一批题，两次跑出两套分类。**

平均 22.7 秒/题（含那次 124 秒超时）。

## 四、可复现性专项测试

5 题 × 3 次，固定输入：

| 用例 | 三次结果 | 稳定？ |
|---|---|---|
| 干净-导数 | method_gap / calculation_error / method_gap | ✗ |
| 干净-积分 | misread_question / concept_misunderstanding / method_gap | ✗ |
| 残题-极限 | method_gap ×3（但 conf 0.0 / 0.9 / 1.0） | ✓ 分类同，置信度仍飘 |
| 残题-偏导 | misread_question / concept_misunderstanding / 超时降级 | ✗ |
| 残题-混合 | concept_misunderstanding / misread_question / method_gap | ✗ |

**分类完全一致：1/5。**

注意"干净-积分"：一道人写的、毫无 OCR 噪声的题，三次跑出**三个不同分类**。
所以这不能归因于 OCR 质量，是模型本身的能力问题。

## 五、置信度信号：能用，但不能当闸门

做了一组对照（干净题 vs OCR 残题）：

| 输入 | 模型给的置信度 |
|---|---|
| 干净题（f(x)=x²+2x+1 求导） | **1** |
| 干净题（定积分） | **1** |
| OCR 残题 | **0** |

模型**确实能区分**"看得懂"和"看不懂"，自评信号有意义。

但结合第四节看：同一道题三次跑，置信度能在 `0.0` 和 `1.0` 之间跳。
也就是说模型会在**随机分类**上给出**满把握**。

> 队长协议里 `error_confidence < 0.5 不入库` 这道闸门，前提是"置信度反映真实把握度"。
> 在 0.5b 上这个前提不成立——它只反映模型这一次抽到了什么。
> 所以这道闸门拦不住垃圾数据，只能拦住模型自认没把握的那些。

## 六、顺带发现并修掉的问题

### 1. `error_type_label` 与 `error_type` 错配（已修）

真机实测到的错配：

| error_type | 模型给的 label | 正确 label |
|---|---|---|
| `misread_question` | 函数定义错误 | 审题偏差 |
| `method_gap` | 区间外函数与区间内函数的函数关系 | 方法缺失 |
| `method_gap` | 计算失误 | 方法缺失 |

协议里 label 是给人看的，必须与 code 一一对应。
**处理**：新增 `normalize_error_analysis()`，以 `error_type` 为准按映射表覆盖 label，
顺带把 confidence 收敛成 float、knowledge_points 强转成数组。不信模型的 label。

### 2. 偶发 124 秒超时

40 次调用里出现 2 次（约 5%），卡在 `REQUEST_TIMEOUT=120` 边界上被判降级。
0.5b 正常 5 秒出结果，124 秒说明是 Ollama 侧卡顿（疑似模型卸载/重载或资源争用），
不是 prompt 太长。**暂时不调超时**，记着这个现象，7b 到位后如果更频繁再处理。

### 3. `AIResponse` 缺 `retries` 字段

联调脚本要统计重试次数时发现没有这个字段，补上了（成功路径记实际重试次数，
降级路径记 `MAX_RETRY`）。

## 七、对结论的自我修正

9/21 早些时候我在《回复队长_AI协议确认》里写的是：

> "7 道已解析错题仅 1 道自动入库，6 道判待复核（0.5b 在背模板）"

那个结论是**在自由文本模式下**测的，当时还没开 `format=json`。
真机联调后要改成：

> 开 `format=json` 后格式问题解决了（6/7 通过校验），
> 但分类内容不可复现（5 题仅 1 题稳定），所以自动入库仍然不可行。

**原因变了，结论没变。** 但原因必须改，因为它决定了催 7b 的理由是否站得住。
