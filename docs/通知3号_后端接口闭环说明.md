# 三号（黄谌佳）后端接口说明：录入 → 分析 → 确认 → 统计

发件人：二号 陈萱燕 Mireya　日期：2026年10月20日
适用：前端录入页、复核页、统计页的联调

后端已把"人工补录闭环"的五个接口补齐并按队长 v2.2 的四项审查意见改完。
本文只讲**你调接口时要知道的东西**：请求怎么发、返回怎么读、空值代表什么、
错误码怎么处理、状态怎么流转。**接口地址统一是 `http://127.0.0.1:8000`**。

---

## 一 先记住两个映射（最容易搞混）

前端表单里的字段名和数据库列名不一样，别照着数据库猜：

| 前端 / 接口字段 | 数据库列 | 含义 |
|---|---|---|
| `answer` | `wrong_answer_text` | **学生的**原始作答（他做错的那个答案） |
| `reference_answer` | `answer_text` | **标准/参考**答案 |

另外 `error_type` 存的永远是四个英文 code 之一，中文名（`error_type_label`）
由后端按 code 现算返回，**数据库里没有 label 这一列**，别去找。

四个合法 code：

| code | 页面显示 |
|---|---|
| `concept_misunderstanding` | 概念不清 |
| `calculation_error` | 计算失误 |
| `misread_question` | 审题偏差 |
| `method_gap` | 方法缺失 |

## 二 五个接口

### 1 新增错题 `POST /errors`

请求：

```json
{
  "username": "test",
  "question": "设 f(x,y)=x²y，求对 x 的偏导在 (1,1) 处的值",
  "subject": "考研数学",
  "answer": "我算的是 2",
  "reference_answer": "4",
  "tag": "偏导数"
}
```

`answer` / `reference_answer` 可以不传（不传 = 本次不填）。
**强烈建议录入页就把 `answer` 填上**——没有学生作答时 AI 归因的置信度会被
后端强制成 0 并直接交人工复核，等于白跑一次分析。

响应：`{"id": 33, "ocr_quality": 82, "answer_recorded": true}`

- `answer_recorded` 是后端确认"作答确实写进去了"，前端可以拿它提示用户。
- 为空字符串会被当成"没有作答"，不是"未知"。

### 2 查询列表 `GET /errors`

`GET /errors?limit=50&subject_code=POSTGRAD_MATH`

返回 `{"count": n, "items": [...]}`，每条含：
`id / question_text / wrong_answer_text / answer_text / review_flag /
error_type / error_confidence / ocr_quality / subject / subject_code`。

列表页要显示"作答"就用 `wrong_answer_text` 和 `answer_text`（表里字段全给了）。

### 3 补录 / 修订作答 `PATCH /errors/{id}/answer`

请求：`{"answer": "我算的是 2x=4，抄成了 2"}`
只传要改的字段，另一个不传就不动（`null` 表示"不改"，不是"清空"；
要清空就传空字符串）。

响应：

```json
{"id": 33, "answer_recorded": true, "reference_answer_recorded": true,
 "changed": true, "review_flag": "pending_review",
 "previous_conclusion_invalidated": true,
 "note": "作答内容已变更，已确认分类退回待复核，旧结论已归档"}
```

**⚠️ 这里有一条会影响你页面的规则**：作答是 AI 归因的输入，改了输入，
旧的"已确认"结论就不再算数。所以**内容真的变了**时，后端会把这条退回到
`pending_review`，页面上原来的"已确认"标记要跟着变灰/变回待复核；
后端返回 `previous_conclusion_invalidated: true` 就是在告诉你这件事。
内容没变的重复提交不会重置（`changed: false`），所以不用担心误触。

### 4 再次分析 `POST /errors/{id}/analyze`

可选参数 `?force=true`。

成功响应：

```json
{"id": 33, "code": 0, "ok": true,
 "suggested_error_type": "calculation_error",
 "suggested_error_type_label": "计算失误",
 "error_confidence": 0.8,
 "answer_placeholder": false,
 "answer_recorded": true,
 "review_flag": "pending_review",
 "previous_review_flag": "confirmed",
 "note": "AI 候选错因，未经人工确认不计入统计",
 "elapsed_ms": 4210}
```

要点：

- `suggested_error_type` 只是**AI 候选**，后端**不会**把它写进 `error_type`。
  要生效必须走第 5 个接口由人工确认。
- `review_flag` 在成功返回**永远跟着库里的真实值**走（后端是回读数据库后返回的）。
  重分析成功会让这条变成 `pending_review`，所以**已确认的题重跑一遍就会退回待复核**，
  页面别以为它还确认着。`previous_review_flag` 告诉你重跑前是什么。
- `force=true` 的用处：已 `confirmed` 的题默认不允许重跑（返回 409），
  加 `?force=true` 才跑。跑了之后它会退回 `pending_review`，需要重新人工确认。
- 失败响应：`{"id":33,"code":1,"ok":false,"error":"...","raw_reason":"..."}`。
  **失败时后端不写库**，页面上这条的解析和状态都保持原样，别清空。

### 5 人工确认 `PATCH /errors/{id}/review`

请求：`{"decision": "confirmed", "error_type": "calculation_error", "note": "抄写失误"}`

响应：`{"id":33,"review_flag":"confirmed","error_type":"calculation_error",
"error_type_label":"计算失误","answer_recorded":true}`

- `decision` 只有两个值：`confirmed`（确认）/ `rejected`（判定 AI 归因不成立，退回待复核）。
- `error_type` 可以不传：这条如果**已经有**合法分类，就会沿用旧的确认；
  如果**既没传、库里也没有**，后端返回 **400 且不改任何状态**——
  这是防止出现"已确认但没分类"的脏数据。页面要能把这个 400 的提示显示出来，
  提示用户先选一个错因再点确认。
- `rejected` 不要求分类（退回待复核本来就不给结论）。

### 附 历史归档 `GET /errors/{id}/history`（复核页可选）

```json
{"id":33,"count":2,"history":[{"event":"answer_changed","review_flag":"confirmed",
 "error_type":"calculation_error","wrong_answer_text":"我算的是 2",
 "reason":"学生/参考答案被修改，原已确认分类退回待复核","created_at":"..."}]}
```

什么时候会产生记录：改了作答（`answer_changed`）、force 重跑分析（`reanalyzed`）、
人工覆盖了已有的已确认结论（`review_changed`）。复核页想显示"这条为什么退回待复核"就读它。

## 三 状态转换表（前端照这个做）

| 当前状态 | 操作 | 变成 | 说明 |
|---|---|---|---|
| 新建 | — | `pending_review` | 待复核 |
| `pending_review` | 分析成功 | `pending_review` | AI 只给候选，状态不变 |
| `pending_review` | 分析失败 | `pending_review` | 不写库，页面保持原样 |
| `confirmed` | 分析（不带 force） | 409 报错 | 已确认的题不许悄悄覆盖 |
| `confirmed` | 分析（force=true） | `pending_review` | 旧结论归档，需重新确认 |
| `pending_review` | 确认 + 合法分类 | `confirmed` | 计入统计 |
| `confirmed` | 改作答（内容变了） | `pending_review` | 旧结论归档，退出统计 |
| `confirmed` | 改作答（内容没变） | `confirmed` | 不动 |
| 任意 | rejected | `pending_review` | 退回待复核 |

**统计口径**：只有 `review_flag != 'pending_review'` 且 `error_type` 非空
才算"已确认"，才会进饼图/雷达图。所以上面每次退回 `pending_review`，
统计数字会当场减一——这是对的，不是 bug。

## 四 错误码

| 码 | 什么时候 | 前端怎么处理 |
|---|---|---|
| 400 | 参数不合法（如 decision 写错、error_type 不是四个之一、confirmed 却没有分类） | 直接把响应里的 `detail` 显示给用户，那是中文说明 |
| 404 | 错题 id 不存在 | 提示记录已删除 |
| 409 | 已 confirmed 的题不加 force 就重跑 | 弹个"已确认，是否强制重跑？"，用户点是就带 `?force=true` 再发 |
